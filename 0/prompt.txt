My top three solutions, ranked

1. Accept submissions immediately and process GitHub work through a durable queue.

Save the submission, its server receipt time and its processing job atomically. Return a receipt immediately. During a GitHub outage, classify remote verification as pending rather than rejecting an otherwise valid submission. Authentication, membership, required fields and deadline checks still apply.

A worker then verifies access, captures code and prepares jury access through resumable steps. It must respect retry headers, distinguish permanent permission failures from transient failures, and record diagnostic response details. Closing submissions and advancing the event must not wait for GitHub.

Use explicit states for verification, snapshot completeness and jury access. A nullable fork URL cannot represent all three.

Why first: This directly prevents GitHub failures from turning into lost submission opportunities.

Tradeoff: Receipt is provisional until remote requirements are verified. The interface and event rules must make that distinction clear.

2. Replace thousands of individual REST operations with bulk capture and reuse.

Fetch repository contents once for review, using a commit specific archive or Git checkout. Transfer Entire refs in batches through Git, including legacy checkpoint branches. Reuse the captured material for subsequent review attempts.

Where REST copying remains, use the SHA already returned by reference discovery and skip unchanged destination refs. Make checkpoint collection an explicit requirement rather than automatically doing it for every challenge. Archive API (https://docs.github.com/en/rest/repos/contents#download-a-repository-archive-tar).

Why second: A queue alone makes excessive work orderly; it does not make that work affordable within the judging window.

Tradeoff: Bulk processing needs limits for repository size and transfer duration. Git operations also need pacing. A normal source archive does not contain all Git history or custom Entire refs.

3. Establish repository access early and provide an independent deadline fallback.

Verify private repository access and prepare jury permissions during the event, rather than doing everything at the deadline. Fix invitation pagination.

Define exactly which code version is submitted. Record an immutable commit identifier and preserve that version; do not later synchronize whatever happens to be on the default branch. If GitHub is unavailable, provide an authenticated code archive upload with a server receipt timestamp, including a checkpoint bundle where required.

Why third: A queue preserves the submission request, but cannot retrieve code while GitHub is unavailable. An independently received artifact also preserves what was submitted on time.

Tradeoff: This adds participant workflow and artifact handling. Without it, the event must explicitly accept delayed verification and the remaining uncertainty about deadline contents.

I recommend implementing solutions 1 and 2 together, with solution 3 as the outage contingency. The strongest objection is implementation scope, but merely increasing quota leaves verification failures, timeouts and stale snapshots unresolved. A second PAT belonging to the same user also shares that user’s quota; it is not independent capacity. GitHub authentication limits (https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

Before declaring readiness, test 150 submissions with repeated updates, GitHub throttling, an outage, worker termination and more than 100 pending invitations. The acceptance criteria should include durable receipts, resumable processing and exact captured commit versions, not just successful HTTP responses.
